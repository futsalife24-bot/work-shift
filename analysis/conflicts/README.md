## 再現した問題

### F1: 応援・休職が週休の「解消不能」理由に混入する

`staffEval`は応援の週休条件と、休職を含む週の週休条件を除外している（`src/app.js:482`付近）。一方、`detectImpossible`の週休候補判定（同`:602`付近）にはこの除外がない。

架空の応援を28日空欄、別の社員を28日休職にした。同じ対象に対する`staffEval`の警告は両者とも0件だが、`detectImpossible`には「第1〜4週に週休・非番を置ける日がありません」が各4件、合計8件出る。

影響: `runSolve`は赤警告が残り、解消不能理由が0件の場合にだけ別案を自動探索する（同`:1572`付近）。そのため、この不要な理由があると別案探索が抑制され、解消不能の説明にも混ざる。判定差8件は実行で再現、別案抑制の影響は呼出条件から確認した。今回、実際の60,000反復を伴う`runSolve`全体は実行していない。

最小修正候補: `detectImpossible`の週ごとの判定を、応援・休職に関する`staffEval`の既存条件と一致させる。通常社員の週休候補0日の警告は維持する。製品への採用・実装は未実施。

### F2: 固定入力とセルロックの優先順位が探索・書戻しで違う

再現手順（実際の既存パレット操作を含む）:

1. 架空社員の初週を6連勤＋7日目の希望休にする。他の勤務をロックし、探索で動かないようにする。
2. 希望休のセルをパレットから8時勤務へ変更してロックする。現行UIはこの操作で希望休の固定入力を残す。
3. `solve`と`applySolution`を実行する。

`solve`は固定入力をロックより先に採用するため7日目を`OF`とする（同`:647`）。`applySolution`はロックされたセルを書き換えず、7日目の`W8`を維持する（同`:895`）。探索結果に7連勤警告は0件、書戻し後のセルには7連勤警告が1件あり、最終チェックも「不一致 1件」を表示する。保存後の再読込でもセル・固定入力・警告は同一だった。保存復元の破損ではなく、書戻し前後の不一致である。

影響: `runSolve`は書戻し前の`res.g`で成功・警告の案内を決めるため、実際に残ったセルと案内が一致しない可能性がある。ただし今回のfixtureには他の人数・区担当の警告もあり、「生成しました」の誤表示そのものは未再現。通常の勤務表と最終チェックには書戻し後の警告が現れることを区別する。

最小修正候補: 書戻し後の`gridFromCells`を使って案内用の評価を再計算し、固定入力との不一致も明示する。根本的には固定入力とロックが衝突した時の優先順位を探索・書戻しで統一する必要がある。希望休と手動ロックのどちらを優先するかは、既存状態を一方的に上書きせず仕様判断後に実装する。今回は候補の提示まで。
